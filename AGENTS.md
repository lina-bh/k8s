# AGENTS.md

## Attribution

* Each comment an agent writes or substantially rewrites SHOULD end with an
  attribution line of the form `Assisted-by: HARNESS:MODEL`, in the file's own
  comment syntax:

  ```yaml
  # Drop duplicated kubelet metrics.
  # Assisted-by: Claude Code:claude-opus-5-5
  ```

* `HARNESS` is the agent program (for example `Claude Code`, `Codex CLI`,
  `pi`), not the vendor. `MODEL` is the exact model identifier the harness
  reports (for example `claude-opus-5-5`), not a marketing name.
* If either part cannot be determined, MUST write `unknown` in its place
  rather than guess.
* The format is adapted from the Linux kernel's
  `Assisted-by: AGENT_NAME:MODEL_VERSION` commit trailer.
* This applies to comments only. Commit attribution is left to the agent's
  configuration.

## Layout

### Clusters

* Flux v2.10.0 reconciles this repository from `main`. `clusters/CLUSTER/` is
  the root for each cluster, synced by the `flux-system` Kustomization in
  `clusters/CLUSTER/flux-system/gotk-sync.yaml`.
  * `melee` is the home cluster. It was rebuilt after running k3s, and its
    apps are being redeployed one at a time.
  * `oke` runs on Oracle Kubernetes Engine (`uk-london-1`). The `oke` kubectl
    context reaches the API server through the Tailscale operator's API
    server proxy, so breaking `tailscale-operator` on OKE also cuts off
    `kubectl` access.
  * `clusters/melee_old/` holds melee's overlays from before the rebuild. No
    Flux instance reconciles it, and it does not build: it lists a
    `flux-system` directory that no longer exists. When an app is
    redeployed, its overlay files move (`git mv`) into `clusters/melee/`.
* `clusters/CLUSTER/flux-system/gotk-*.yaml` are generated by `flux` and
  SHOULD NOT be edited by hand.

### Apps

* Each app lives in `apps/NAMESPACE/APP/`:
  * `ks.yaml` holds the app's Flux `Kustomization` objects (see below).
  * `kustomization.yaml` sets `namespace: NAMESPACE` and lists `ks.yaml`.
  * `base/` holds the manifests, which omit `metadata.namespace`. Variants
    sit beside it (`jfin/intel`, `generic-device-plugin/tun`, `zot/registry`,
    `parr/bm`) and are chosen by the Kustomization's `path`.
  * Some bases contain their own Flux sources and Kustomizations, for example
    `apps/cnpg-system/cloudnative-pg/configs/base` and
    `apps/kube-system/intel-gpu-plugin/base`.
* `apps/NAMESPACE/` holds `namespace.yaml` and a `kustomization.yaml` that
  lists it.
  * Every Namespace carries `kustomize.toolkit.fluxcd.io/prune: disabled`, so
    removing it from Git does not delete it or its contents.
  * Namespaces whose pods need extra privileges set
    `pod-security.kubernetes.io/enforce: privileged`.
  * In namespaces that hold a single operator (`external-secrets`,
    `longhorn-system`, `local-path-storage`, `monitoring`, `openebs`,
    `tailscale`, and `cnpg-system` through `cloudnative-pg/`), this
    `kustomization.yaml` also lists the operator's `ks.yaml`, so including
    `apps/NAMESPACE` deploys both. Those operators have no app-level
    `kustomization.yaml`.
  * In other namespaces it lists only `namespace.yaml`, and each app is
    enabled separately. `apps/kube-system/` has no namespace-level files.
* `apps/kustomization.yaml` lists `monitoring`. `clusters/melee` includes
  `../../apps`, which is how melee gets the `monitoring` namespace and
  `prometheus-operator-crds`.
* bitmagnet (`bm`) runs inside Prowlarr's pod. The variant
  `apps/moving-pictures/parr/bm` adds it to the `parr-app` Deployment as a
  second container, along with its own `Cluster` `bm-pg`, and melee points
  the `parr` Kustomization's `path` at it. bitmagnet has no Kustomization,
  Service or Ingress of its own. Prowlarr's indexer for it is set in
  Prowlarr, not in Git, to `http://localhost:3333/torznab`. The pod template
  sets `kubectl.kubernetes.io/default-container: app`, so `kubectl logs` and
  `kubectl exec` default to Prowlarr.
* `components/gluetun/` is a Kustomize Component (see "gluetun").
* `bin/wireguard-to-secret.py NAME PROVIDER < wg.conf` prints a gluetun
  Secret from a WireGuard config. `bin/wireguard-to-env.py < wg.conf` prints
  the same keys as an env file, except `VPN_SERVICE_PROVIDER`, which it does
  not take.

### Enabling and patching apps per cluster

* `clusters/CLUSTER/kustomization.yaml` lists `flux-system` and one directory
  per namespace. `clusters/CLUSTER/NAMESPACE/kustomization.yaml` sets
  `namespace` and lists `../../../apps/NAMESPACE` plus each
  `../../../apps/NAMESPACE/APP` the cluster runs. A new namespace directory
  also has to be added to the cluster root.
* Cluster-specific changes are patches on the Flux `Kustomization`, in
  `clusters/CLUSTER/NAMESPACE/APP.yaml` (named after the Kustomization) and
  listed under `patches`. Most set `spec.patches`, which Flux applies to the
  rendered app (for example `clusters/melee/moving-pictures/postgres.yaml`).
  Some change `spec.path`, `spec.dependsOn` or `spec.targetNamespace`.
* A strategic-merge patch on a Flux `Kustomization` replaces lists such as
  `spec.dependsOn` and `spec.patches` instead of merging them, because
  kustomize has no merge keys for this CRD. To append, use a JSON 6902 patch
  with `op: add` and a path such as `/spec/patches/-`.
* To add resources to an app on one cluster only, point the Kustomization's
  `spec.path` at a cluster directory whose `kustomization.yaml` includes the
  app's base plus the extras, as `clusters/oke/tailscale/operator/` does.
* Cluster-only resources sit in the cluster directory: StorageClasses
  (`clusters/melee/openebs/`), static PVs (`clusters/melee/music/storage/`)
  and shared PVCs (`clusters/melee/moving-pictures/media.yaml`).

## Flux Kustomizations (`ks.yaml`)

Most follow this template:

```yaml
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: APP
spec:
  dependsOn: []
  interval: 1h
  path: ./apps/NAMESPACE/APP/base
  prune: true
  sourceRef:
    kind: GitRepository
    namespace: flux-system
    name: flux-system
  targetNamespace: NAMESPACE
  timeout: 15m
  wait: true
```

* The Kustomization object lives in the app's namespace, so a `dependsOn`
  entry for a Kustomization in another namespace needs `namespace:`.
* The `targetNamespace` has to exist before the Kustomization is applied;
  kustomize-controller does not create it. Kustomizations that apply only
  cluster-scoped objects omit it (`pg-password`, `oci`).
* With `wait: true` a Kustomization becomes Ready only once everything it
  applied is healthy. With `wait: false` it is Ready as soon as the apply
  succeeds, before a HelmRelease it applied has installed any CRDs, so a
  Kustomization that others list in `dependsOn` SHOULD set `wait: true`.

### `dependsOn`

* A Kustomization SHOULD list another in `dependsOn` only when its own
  objects cannot be applied without it, which in practice means the other
  installs the CRDs (and admission webhooks) for custom resources it applies.
* SHOULD NOT add an entry for something that only has to exist at run time:
  a Secret, generator or secret store, a database `Cluster`, an image
  catalog, a StorageClass, a ProxyGroup, or another app's Service or API.
  Objects that refer to it still apply, and CloudNativePG and External
  Secrets retry until it appears (see "Flux, Helm, CloudNativePG and External
  Secrets behaviour").
* The entry goes on the Kustomization that applies the custom resources. A
  Kustomization that applies only Flux sources and inner Kustomizations
  needs none; the inner one carries it, as
  `apps/cnpg-system/cloudnative-pg/configs/base/ks.yaml` (`artifacts`) and
  `apps/kube-system/intel-gpu-plugin/base/fluxtomisation_nfr.yaml` do.
* The CRD providers:
  * `cloudnative-pg` (namespace `cnpg-system`): `Cluster`, `Database`,
    `DatabaseRole`, `ClusterImageCatalog`;
  * `external-secrets-operator` (namespace `external-secrets`):
    `ExternalSecret`, `ClusterSecretStore`, `Password`, `ClusterGenerator`;
  * `operator` (namespace `tailscale`): `ProxyGroup`, `ProxyClass`;
  * `node-feature-discovery` (namespace `kube-system`): `NodeFeatureRule`;
  * `prometheus-operator-crds` (namespace `monitoring`): the
    `monitoring.coreos.com` kinds.

## Manifests

* Hand-written YAML follows `yamlfmt.yml`: each file starts with `---`, and
  list items are not indented under their key. `yamlfmt -lint FILE` checks a
  file.
* Container images pin both a tag and a digest (`TAG@sha256:...`).
  OCIRepositories pin `ref.tag` and `ref.digest`; GitRepositories pin
  `ref.tag` or `ref.commit`.
* Renovate scans only `apps/` and `clusters/oke/` (`renovate.json`), so image
  and chart versions SHOULD live under `apps/`, not `clusters/melee/`.
* Workloads carry `app.kubernetes.io/name`, plus `app.kubernetes.io/component`
  where an app has several.
* New apps SHOULD name every object explicitly as `APP-...`, including
  generated ConfigMaps (`iv-app`, `iv-pg`, `iv-cfg`), and SHOULD set
  `app.kubernetes.io/name` directly on each object, its selectors and its pod
  template, as `apps/iv/iv/base` does. They SHOULD NOT use `namePrefix` or
  kustomize `labels`.
* Older apps (for example `sarr`, `qbt`, `miniflux`) give objects short names
  (`app`, `role`, `db`) and set `namePrefix: APP-` and `labels` with
  `includeSelectors: true` in `base/kustomization.yaml`.
  * kustomize does not apply the prefix in fields it does not know about,
    such as `ExternalSecret.spec.target.name` and
    `DatabaseRole.spec.passwordSecret.name`, or in references to Secrets
    outside the build, so those spell out the prefixed name (`sarr-role`).
  * Converting one of these apps renames its objects: Flux creates the new
    objects and prunes the old ones, and a renamed StatefulSet gets new PVCs
    from its `volumeClaimTemplates`. Existing apps SHOULD keep their style
    unless the rename is planned as a migration.
  * `parr` is converted part-way: its objects are named explicitly
    (`parr-app`, `parr-role`), but it still sets `labels`.
* Settings repeated across containers are kept in a ConfigMap annotated
  `config.kubernetes.io/local-config: "true"` and copied in with kustomize
  `replacements`, for example in `apps/iv/iv/base` and
  `apps/miniflux/miniflux/base`. The ConfigMap itself is not emitted.
* App pods set `automountServiceAccountToken: false`, and many set
  `hostUsers: false` (`jfin`, `sarr` and `nd` set it to `true`). App
  containers run as non-root with `readOnlyRootFilesystem: true`,
  `allowPrivilegeEscalation: false` and all capabilities dropped. The gluetun
  sidecar is the exception.

## Secrets

* No secret values are committed.
* Generated secrets come from External Secrets generators, with
  `refreshPolicy: CreatedOnce` and `target.deletionPolicy: Delete`: the
  `pg-password` `ClusterGenerator` for database roles, or a namespace's
  `keygen` `Password` generator (`apps/iv/keygen`,
  `apps/moving-pictures/keygen`) for other keys.
* The Prowlarr and Sonarr API keys come from `keygen`. `parr-apikey` holds
  `PROWLARR__AUTH__APIKEY` and is loaded with `envFrom`; Prowlarr reads its
  key only from the `Prowlarr:Auth` options section, so `PROWLARR__APIKEY`
  is ignored. `sarr-apikey` holds `apikey`, which `sarr` reads through
  `secretKeyRef` and `recyclarr` mounts as a file.
* On OKE, the `ClusterSecretStore` `oci` (OCI Vault, Kustomization
  `external-secrets/oci`) supplies other values, for example
  `clusters/oke/tailscale/operator/externalsecret_operator-oauth.yaml`.
* melee has no secret store. Secrets that cannot be generated, such as the
  `gluetun` WireGuard settings, are created by hand and are not in Git.

## PostgreSQL (CloudNativePG)

* Shared database: a namespace's `postgres` app runs a `Cluster` named `pg`
  (`apps/moving-pictures/postgres`). Each app that uses it has:
  * an `ExternalSecret` generated from the `pg-password` `ClusterGenerator`,
    of type `kubernetes.io/basic-auth`, targeting `APP-role`;
  * a `DatabaseRole` with `login: true` that reads its password from that
    secret;
  * a `Database` owned by that role.

  The app connects through the `pg-rw` Service. Its `ks.yaml` lists
  `cloudnative-pg` (namespace `cnpg-system`) and `external-secrets-operator`
  (namespace `external-secrets`) under `dependsOn`, for the CRDs, but not
  `pg-password` or `postgres`. On first deploy the app can fail to log in and
  restart a few times until the role's password exists and CloudNativePG has
  applied it (seen with `parr`).
* Dedicated database: the app's base has its own `Cluster`, and the app
  reads the operator's `CLUSTER-app` Secret (key `fqdn-uri`). `iv` (`iv-pg`),
  `miniflux` and bitmagnet (`bm-pg`) work this way.
* Clusters run `instances: 1` with `enablePDB: false`, and take their image
  from `imageCatalogRef` to the `ClusterImageCatalog`
  `postgresql-minimal-trixie`, major 18. `miniflux` still sets `imageName`.
* Bases leave `storage.storageClass` unset, and each cluster patches it in:
  `nv2-ext4` on melee, `longhorn` on OKE.
* No backups are configured.

## Ingress

* Apps are exposed on the tailnet (`lamancha-alhena.ts.net`) by the Tailscale
  operator. An Ingress sets `ingressClassName: tailscale`, lists the short
  hostname under `tls.hosts`, and carries
  `tailscale.com/proxy-group: ingress` to use the shared `ProxyGroup`
  `ingress` from `apps/tailscale/tailscale-operator/configs`. `jfin` and `nd`
  do not use the ProxyGroup yet.
* Each cluster sets its ProxyGroup's `hostnamePrefix` and the operator's
  hostname in `clusters/CLUSTER/tailscale/`.

## Storage and devices

* melee uses OpenEBS LVM LocalPV on the volume group `nv2`, through the
  StorageClasses `nv2-ext4` and `nv2-ext4-shared` (`shared: yes`), both
  mounted with an SELinux `context=` option.
* melee has no default StorageClass, so a claim without one stays Pending.
  Bases leave `storageClassName` unset on PVCs and `volumeClaimTemplates`,
  and melee's overlays patch in `nv2-ext4`
  (`clusters/melee/moving-pictures/qbt.yaml`, `sarr.yaml`).
* `moving-pictures` on melee shares the PVC `media` (`nv2-ext4-shared`),
  mounted at `/media` by `qbt` and `sarr`. `jfin` mounts only its `tv`
  directory, read-only, at `/media/tv`. Every app sees the same paths, so no
  remote path mappings are needed and imports can hardlink. The volume's
  group is 995 with the setgid bit set.
* melee mounts host data through static local PVs with
  `storageClassName: ""` (`clusters/melee/music/storage/`). Their size comes
  from a local-config ConfigMap through `replacements`.
* OKE uses Longhorn (`apps/longhorn-system/longhorn`).
* `generic-device-plugin` exposes `/dev/net/tun` as `devic.es/tun`, and
  `intel-gpu-plugin` exposes `gpu.intel.com/i915` (used by `jfin/intel`).

## gluetun

* `components/gluetun` adds gluetun as a native sidecar (an init container
  with `restartPolicy: Always`) to each Deployment or StatefulSet annotated
  `io.github.lina-bh/gluetun: enabled`.
* An app opts in by listing the component under `components` in
  `base/kustomization.yaml`. It MAY generate a `gluetun-overrides` ConfigMap
  (for example `SERVER_REGIONS`, `FIREWALL_VPN_INPUT_PORTS`), as
  `apps/moving-pictures/qbt/base` does; the sidecar's reference to it is
  optional. The sidecar loads it after `config.sh` and the `gluetun` Secret,
  and `envFrom` takes the last source's value, so a key set there replaces
  the default rather than adding to it.
* The component's ConfigMaps take the app's `namePrefix`. An app without one
  (`parr`) emits `gluetun-config-HASH`, and since every app shares
  `config.sh`, a second app without a prefix in the same namespace would
  emit and apply the same object.
* gluetun's firewall accepts connections on the pod's network interface only
  to the ports in `FIREWALL_INPUT_PORTS`, so without them the app's Service
  and Ingress cannot reach it. `config.sh` sets `9999`, the health server
  that the startup probe checks. Each app's `gluetun-overrides` sets it to
  `9999` followed by its containers' ports, and has to repeat `9999`:
  `9999,8080` for `qbt`, and `9999,9696,3333` for `parr` with bitmagnet,
  which `parr/bm` merges over the base's value.
* gluetun accepts all traffic on `lo`, so containers in one pod reach each
  other on `localhost` without `FIREWALL_INPUT_PORTS`, as Prowlarr reaches
  bitmagnet.
* Outbound traffic leaves through the VPN, except to melee's Service CIDR
  (`10.96.0.0/12`), which `config.sh` lists in `FIREWALL_OUTBOUND_SUBNETS`.
* The pod keeps `dnsPolicy: ClusterFirst`, with `ndots:1`. gluetun (v3.41.0
  and later) reads kube-dns from `/etc/resolv.conf` once, when its process
  starts, then points the file, which every container in the pod shares, at
  itself. It forwards local names (no dot, or ending in `.local` and
  similar) to kube-dns and the rest to its upstream over DNS over TLS, so the
  app can reach cluster Services such as `pg-rw`. Prowlarr (`parr`) relies on
  this for `pg-rw` and `sarr-app`.
  * If the gluetun container restarts without the pod, it reads back
    `127.0.0.1` and local names stop resolving until the pod is recreated.
    This comes from gluetun's source and has not been observed.
* Renovate does not update the component's image pin: the `components/`
  pattern under `kubernetes` in `renovate.json` lacks its closing `/`, so
  Renovate treats it as a glob, which matches nothing.
* The namespace needs the `gluetun` Secret with `VPN_SERVICE_PROVIDER` and
  the WireGuard settings, which the sidecars share. `config.sh` does not set
  a provider. The sidecar requests `devic.es/tun` and adds
  `NET_ADMIN`, so the namespace has to enforce the `privileged` pod security
  level.

## Checking changes

* `kubectl` is in `sandbox.excludedCommands`, so it runs outside the agent
  sandbox with access to `~/.kube`. Other commands that talk to a cluster
  (`flux`, `helm`) need `~/.kube/config`, which the sandbox cannot read, so
  the user has to run them.
* `just reconcile` runs `git push origin main` before reconciling. Agents
  MUST NOT run it.
* Tools come from `mise.toml`; `yamlfmt` is installed separately.
* `just` recipes take `cluster=NAME` (default `melee`) and render the cluster
  with flate:
  * `just build` renders every Kustomization and HelmRelease, and
    `just inflate` only the Kustomizations;
  * `just diff` diffs the rendered cluster against the merge base with the
    upstream branch;
    `flate diff all --path=clusters/CLUSTER --base=HEAD` shows only
    uncommitted changes;
  * `just lint` runs kube-linter (`kube-linter.yaml`) and kubeconform, which
    validates custom resources against the datreeio CRDs catalog. On melee,
    kubeconform passes and kube-linter already reports 153 findings on
    `main`, so check the findings for the changed objects rather than the
    exit status;
  * `just renovate` runs a local Renovate dry run and needs `gh auth token`;
  * `kind-up` and `kind-down` are stale: `./k8s/clusters/dev` and
    `kind/dev.yaml` do not exist.
* In the agent sandbox, flate's default cache and just's runtime directory
  are read-only. Point both at a writable directory:

  ```sh
  JUST_TEMPDIR="$TMPDIR" FLATE_CACHE_DIR="$TMPDIR/flate" just lint
  ```

* `flate build ks NAME --path=clusters/CLUSTER -n NAMESPACE` renders a single
  Kustomization.
* Without flate, a base can be rendered with `kubectl kustomize` and checked
  with `kubeconform -strict -summary -ignore-missing-schemas`, which skips
  custom resources. Several bases (for example
  `apps/moving-pictures/postgres/base`) have no `kustomization.yaml` and rely
  on kustomize-controller generating one from every manifest in the
  directory tree, so `kubectl kustomize` fails on them.
* kubeconform downloads its schemas, so it needs network access.

## Flux, Helm, CloudNativePG and External Secrets behaviour

Checked against kustomize-controller v1.10.1, fluxcd/pkg/ssa v0.83.0,
CloudNativePG 1.30.1 and External Secrets v2.14.0:

* When a Flux `Kustomization` takes over an object that already exists, for
  example one created by `kubectl apply`, it patches the object in place with
  server-side apply. It takes over the fields owned by any field manager whose
  name starts with `kubectl`, and by `before-first-apply`, so a field that
  only those set and that is missing from Git is removed. Fields owned by
  other managers stay. The controller's `--override-manager` flag adds
  managers to take over, and melee's kustomize-controller does not set it.
  It also removes the `kubectl.kubernetes.io/last-applied-configuration`
  annotation.
* Deleting a `Kustomization`, for example by removing its `ks.yaml` from a
  cluster, runs its finalizer. With the default `deletionPolicy`
  (`MirrorPrune`) and `prune: true`, it deletes every object in its
  inventory whose live labels still name it
  (`kustomize.toolkit.fluxcd.io/name` and `namespace`), except objects
  annotated `kustomize.toolkit.fluxcd.io/prune: disabled`. An object that
  another Kustomization has applied since carries that one's labels and is
  kept. A suspended Kustomization deletes nothing.
  * The two reconciles run in no fixed order, so moving a stateful object to
    another Kustomization needs the annotation first. CloudNativePG's PVCs
    have an ownerReference to their `Cluster`, so deleting the `Cluster`
    deletes its volumes.
  * To set the annotation on a live object without putting it in Git, use
    `kubectl annotate --field-manager flux-client-side-apply`. kubectl's
    default manager for `annotate` is `kubectl-annotate`. That name starts
    with `kubectl`, so Flux takes the field over and removes the annotation
    on the next reconcile. `flux-client-side-apply` matches neither
    `kubectl` nor `before-first-apply`, so the annotation stays. `bm-pg`'s
    annotation was set this way on 2026-11-11 and was still there after
    `parr`'s later reconciles. `kubectl get --show-managed-fields` shows
    which manager owns a field.
  * Objects on melee that carry the annotation this way (not in Git):
    * `bm-pg` (`Cluster`), from its move from the `bm` Kustomization to
      `parr`;
    * the ExternalSecrets `qui-role` and `qui-session`, the Database
      `qui-db` and the DatabaseRole `qui-role`, for the move from the `qui`
      Kustomization to `qbt` (`apps/moving-pictures/qbt/qui`).

    To remove it once a move has finished:

    ```sh
    kubectl annotate -n moving-pictures cluster bm-pg \
      kustomize.toolkit.fluxcd.io/prune-
    kubectl annotate -n moving-pictures \
      externalsecret/qui-role externalsecret/qui-session \
      database/qui-db databaserole/qui-role \
      kustomize.toolkit.fluxcd.io/prune-
    ```
* Flux deletes and recreates an object only when both of these hold:
  * the apply fails with an Invalid (422), Conflict or "immutable" error;
  * `spec.force: true` is set, or the object carries
    `kustomize.toolkit.fluxcd.io/force: enabled`.

  No `Kustomization` here sets `force`. It SHOULD NOT be set on one that
  manages stateful objects.
* A CloudNativePG `Database` defaults to `databaseReclaimPolicy: retain`, so
  deleting the resource leaves the PostgreSQL database in place. Its
  `spec.name`, `spec.cluster` and locale fields cannot be changed after
  creation.
* CloudNativePG's `Cluster` webhook does not look up the image catalog named
  in `imageCatalogRef`, and the operator watches `ImageCatalog`s and
  `ClusterImageCatalog`s and requeues the Clusters that refer to them. A
  Cluster applied before its catalog therefore starts once the catalog
  appears.
* External Secrets' `ExternalSecret` webhook checks only the object itself,
  not the store or generator it refers to. When a sync fails, for example
  because the generator does not exist yet, the controller returns the error
  and controller-runtime requeues it with backoff.

From the Flux HelmRelease documentation (both clusters run helm-controller
v1.7.1):

* `releaseName` defaults to `[<target namespace>-]<name>`, and
  `storageNamespace` to the HelmRelease's namespace. Changing `releaseName`,
  `targetNamespace` or `storageNamespace` on an installed release uninstalls
  it and installs a new one. If the chart templates its CRDs, the uninstall
  deletes them along with every custom resource of those kinds.
* On OKE, the HelmReleases for cloudnative-pg, external-secrets, longhorn and
  tailscale-operator pin `releaseName`, `storageNamespace: flux-system` and
  `targetNamespace` in `clusters/oke/`, so that the shared bases adopted the
  releases installed before the move. These pins MUST NOT be removed or
  changed.

## Commits

* Subjects take the form `SCOPE: summary`, in lower case with no final full
  stop. `SCOPE` is a cluster (`melee`, `oke`), a namespace or an app by its
  upstream name (`invidious` for `iv`, `navidrome` for `nd`), or `aux`,
  `renovate` or `repowide` for repository tooling.
* Renovate's commits use `chore(deps): ...`.
